# Validation

This directory contains case-specific scientific validation workflows for the
framework implementations in this repository.

Unlike the synthetic tests in `tests/`, these validation scripts use research
case data to verify scientific behavior, numerical equivalence, and consistency
with the legacy research workflows.

Validation scripts are intended for scientific verification and regression
checking. They are not required for normal use of the framework.

## Directory Structure

```text
validation/
├── README.md
├── temporal_anomaly/
│   ├── __init__.py
│   ├── config.py

│   └── validate_afghanistan_end_to_end.py
└── statistical_clustering/
    └── ...
```

The validation workflows are organized by framework component so that each
scientific module can be verified independently.

## Temporal Anomaly Validation

The temporal-anomaly validation workflow uses the 21 June 2022 Afghanistan
earthquake case study to verify the scientific behavior of the Temporal Anomaly
Detection Framework and its consistency with the legacy research workflow.

The validation covers four levels:

1. Multi-day TEC time-series preparation
2. Numerical equivalence of the prepared TEC input
3. Numerical equivalence of the temporal anomaly calculation
4. End-to-end reproduction of the Afghanistan case result

Together, these checks verify that the current implementation preserves the
scientific behavior of the original analysis while using the reorganized
software architecture.

### TEC Collection Structural Validation

`validate_afghanistan_tec_collection.py`

Validates the preparation of the multi-day TEC time series used for the
Afghanistan case.

The script checks:

- 46 daily processed GIM datasets
- 25 raw epochs per daily dataset
- selection of the 24 epochs belonging to each target calendar day
- extraction of the nearest GIM grid point to the earthquake epicenter
- combination into a continuous 1104-point hourly TEC series
- absence of duplicate timestamps
- strictly increasing chronological order

Expected grid point:

```text
Latitude:   32.5°
Longitude:  70.0°
```

Expected time range:

```text
2022-05-07 00:00 UT
to
2022-06-21 23:00 UT
```

Expected result:

```text
Afghanistan TEC collection structural validation: PASS
```

### TEC Numerical Equivalence

`validate_afghanistan_tec_equivalence.py`

Compares the TEC series produced by the current data-preparation workflow with
the TEC input generated by the legacy research workflow.

The comparison includes:

- temporal structure
- source-precision equivalence
- float32 representation
- machine-level floating-point differences

The legacy and current TEC values may differ at approximately machine
floating-point precision. Exact binary equality is therefore treated as a
diagnostic rather than the scientific pass criterion.

The scientific equivalence criterion is equality at the source TEC precision
of 0.1 TECU.

Expected result:

```text
Afghanistan TEC numerical equivalence: PASS
```

### Temporal-Anomaly Numerical Equivalence

`validate_afghanistan_temporal_anomaly_equivalence.py`

Compares the current `detect_temporal_anomalies` implementation against the
legacy quartile-based temporal anomaly calculation used for the Afghanistan
case study.

Both implementations operate on the same 46-day TEC input.

The comparison includes:

- observed TEC
- first quartile (Q1)
- median (Q2)
- third quartile (Q3)
- upper anomaly bound
- lower anomaly bound
- anomaly classification

Temporal-anomaly parameters:

```text
Reference window:      15 days
Threshold multiplier:  3.0
```

Expected anomaly counts:

```text
Positive:  37
Normal:    610
Negative:  97
```

Expected result:

```text
Afghanistan temporal-anomaly equivalence: PASS
```

### End-to-End Reproduction

`validate_afghanistan_end_to_end.py`

Runs the complete Temporal Anomaly Detection Framework validation workflow:

```text
processed daily GIM data
    -> fixed-point TEC extraction
    -> calendar-day selection
    -> multi-day TEC combination
    -> temporal anomaly detection
```

The script verifies both the intermediate TEC input and the final temporal
anomaly result.

Expected input:

```text
Daily files:     46
TEC points:      1104
Grid point:      (32.5°, 70.0°)
```

Expected analysis output:

```text
Analysis points: 744
Analysis start:  2022-05-22 00:00 UT
Analysis end:    2022-06-21 23:00 UT

Positive:         37
Normal:          610
Negative:         97
```

Expected result:

```text
Afghanistan end-to-end validation: PASS
```

## Required Local Data

The Afghanistan validation depends on research data and intermediate validation
artifacts that are not distributed with this repository.

The processed daily GIM datasets have filenames of the form:

```text
gim_20220507.npz
gim_20220508.npz
...
gim_20220621.npz
```

The TEC numerical-equivalence validation additionally requires:

```text
old_tec.npz
afghanistan_new_tec_validation.npz
```

The temporal-anomaly legacy-equivalence validation requires the corresponding
legacy GIM data.

These files are local validation resources and are not required for normal use
of the framework.

## Local Data Configuration

Local validation data paths can be configured through environment variables.
This keeps machine-specific paths and research data outside the repository.

The supported variables are:

```text
TEC_PROCESSED_DIR
TEC_LEGACY_GIM_DIR
TEC_LEGACY_TEC_FILE
TEC_NEW_TEC_FILE
```

Example in PowerShell:

```powershell
$env:TEC_PROCESSED_DIR = "C:\path\to\processed"
$env:TEC_LEGACY_GIM_DIR = "C:\path\to\legacy_gim"
$env:TEC_LEGACY_TEC_FILE = "C:\path\to\old_tec.npz"
$env:TEC_NEW_TEC_FILE = "C:\path\to\afghanistan_new_tec_validation.npz"
```

These settings apply to the current PowerShell session and do not need to be
stored in the repository.

If an environment variable is not provided, the validation configuration uses
the default relative paths defined in `temporal_anomaly/config.py`.

## Running the Temporal Anomaly Validation

Run the validation scripts from the repository root:

```powershell
python -m validation.temporal_anomaly.validate_afghanistan_tec_collection

python -m validation.temporal_anomaly.validate_afghanistan_tec_equivalence

python -m validation.temporal_anomaly.validate_afghanistan_temporal_anomaly_equivalence

python -m validation.temporal_anomaly.validate_afghanistan_end_to_end
```

Each script should finish with its corresponding `PASS` message.

## Data Availability

The validation data are not distributed directly with this repository.

GIM/IONEX data used to construct the TEC time series originate from publicly
available Global Ionosphere Map products. Data acquisition and IONEX parsing
are handled separately from the scientific framework.

Users who wish to reproduce the validation should obtain the corresponding
source data and prepare them using the associated GIM data-processing tools.

The scientific implementation in this repository does not require the
Afghanistan validation dataset for general use.

## Tests vs. Validation

The repository distinguishes between software tests and scientific validation:

```text
tests/
    Synthetic and software-level behavior checks.
    Case-specific research data are not required.

validation/
    Case-specific scientific reproduction and legacy-equivalence checks.
    Local research data are required.
```

The synthetic tests verify general software behavior, whereas the validation
scripts provide evidence that the reorganized implementation preserves the
scientific results of the original research workflows.
